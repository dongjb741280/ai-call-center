ABOUT VOXHUB

让每一种声音，都有连接的枢纽。

「声枢」取“声音的枢纽”之意。Vox 代表声音，Hub 代表连接。门户汇聚四个关联项目，帮助团队理解从呼叫接入、坐席运营到 AI 编排和质量验证的完整路径。

ai-call-center 面向人工呼入、呼出和呼叫底座；ai-call-center-web 提供管理工作台；IntelliCall-Pro 探索 AI 优先客服；ai-call-center-test 提供前端自动化回归。它们是独立工程，组合部署时需完成接口与配置集成。

本门户为静态产品介绍网站。演示使用预设内容，不能直接拨号，也不调用真实 AI。业务服务需另外部署。

CAPABILITY STATUS

明确能力，也明确当前边界。

以下状态根据本地项目 README 与文档整理（2026 年 9 月），后续以各项目的最新文档为准。

呼叫中心与工作台 已有实现

呼叫控制、ACD 分配、技能组、多租户、坐席状态、通话统计，以及 Vue 管理界面和 WebRTC 软电话。实际使用需配置数据库、FreeSWITCH、线路与业务权限。

AI 语音闭环 已实测跑通

IntelliCall-Pro 已实测「呼入 → ASR → LLM → TTS → 播放」半双工链路。当前识别和合成为整句处理，不能视为低延迟全双工服务；CPU 上的语音合成速度有限。

知识、工具与合规模块 模块已交付，需集成验证

包括 RAG、业务工具、PII 脱敏、录音加密、留存清理和异步质检。录音与质检默认关闭，需按目标业务启用；合规模块尚未完成实机拨测。

高可用与多副本 配置待实机验证

已有 FreeSWITCH 池化、Kamailio 前置、ASR/TTS 多副本与 track-calls 等代码或配置，但相关配置尚未完成实机拨测，不作可用性或并发量承诺。

自动化回归 测试框架已实现

ai-call-center-test 的 README 记录覆盖 38 个前端页面，提供冒烟、baseline、模块增量和 UI 适配器。覆盖范围不等于当前全部通过，需对目标环境执行验证。

外呼与任务触达 预留 · 规划中

坐席可经工作台与软电话发起呼出并记录结果；任务外呼、预测式外呼、自动外呼，以及号码频控、黑名单与外呼时段等合规策略尚未实现，需在呼叫引擎与合规层面补充。

实时监控与运营大屏 预留 · 规划中

队列与坐席实时看板、通话监听与实时指标大屏尚未实现，当前以历史通话记录与运营报表为主。

工单与客户管理 预留 · 规划中

工单创建与流转、来电弹屏、客户画像与标签等尚未实现，需要独立业务系统，或与现有 CRM 完成接口集成。

开放平台与统一 API 预留 · 规划中

各项目已有内部接口与 WebSocket 能力，但尚未提供统一的开放 API 门户、SDK 与 HTTP IVR 集成规范，面向外部集成需进一步收敛。

ARCHITECTURE

根据业务阶段，组合合适的能力。

人工服务优先

使用 ai-call-center 处理 FreeSWITCH 事件、路由与坐席状态，搭配 ai-call-center-web 做配置、运营与浏览器通话。底层服务采用 Spring Boot、Redis、业务数据库和 MinIO。

AI 优先接待

IntelliCall-Pro 使用 Python + LangGraph 编排通话状态，FunASR 识别语音，LlamaIndex + pgvector 检索知识，CosyVoice 合成回复。当前大模型适配为 Claude，其他模型需按接口接入并验证工具调用。

关于数据部署边界

语音识别、合成、数据库和编排服务可在自有环境运行。是否有数据传出环境，取决于你使用的模型 API 和其他业务接口；使用外部大模型 API 时，相关文本会发送到所选服务。

详细架构与实施状态见 IntelliCall-Pro 架构规格，仓库默认分支若有变化，请从仓库首页进入文档。

GET STARTED

从一条可验证的链路开始。

  1. 准备呼叫底座。

    按照 ai-call-center README 准备 Java、数据库、Redis 与 FreeSWITCH，启动管理服务和呼叫服务，配置分机、网关与拨号计划。

  2. 接入管理工作台。

    按照 ai-call-center-web README 安装依赖并设置后端代理。先确认登录、分机注册、坐席状态和人工通话可用。

  3. 验证 AI 语音闭环。

    按照 IntelliCall-Pro README 安装语音栈与模型、准备 Python 3.10 + uv、配置模型凭据与 FreeSWITCH 连接后，启动编排层：

    cd IntelliCall-Pro/services/orchestrator
uv sync
uv run intellicall

    先验证呼入与语音应答，再逐项接入知识库、工具、人工转接、录音和质检。具体分机和环境变量以仓库 README 为准。

门户的业务场景是能力组合示意。例如回访反馈写入 CRM、跨系统同步对话上下文等，都需要自行对接相应业务接口。

QUALITY ASSURANCE

让持续验证成为日常。

本地 ai-call-center-test 工程通过 Playwright 覆盖登录、仪表盘、软电话，以及管理、服务、呼入、呼出、通话和报表模块。已提供按变更模块执行测试的工具和 CI 配置。

cd ai-call-center-test
npm install
npx playwright install chromium
# 按 README 设置 .env 和测试账号，然后保存登录态
npm run login
npm run test:smoke
npm test

请先确认目标测试环境与专用测试账号，再运行涉及增删改查的用例。该工程尚未在本地配置 GitHub 远程地址，因此门户提供本说明作为入口。

STATIC SITE DEPLOYMENT

门户无需后端，即可发布。

门户只使用 HTML、CSS 和 JavaScript，字体、图标与静态资源随站点提供，不依赖 CDN。Node.js 20+ 仅用于本地预览、构建和检查。

cd voxhub-portal
npm run dev
# 浏览器访问 http://localhost:4173

npm run check
npm run build
npm run preview

GitHub Pages · Actions 发布

  1. 创建 GitHub 仓库。

    建议名称 voxhub-portal。将本目录作为仓库根目录提交，包含 .github/workflows/deploy.yml。

  2. 开启 Pages。

    在仓库 Settings → Pages → Build and deployment 中，将 Source 设为 GitHub Actions。

  3. 推送到 main 分支。

    工作流会检查站点、构建 dist/ 并部署。首次启用 Pages 后，如自动运行已失败，可在 Actions 页面重新运行。

  4. 访问生成的网址。

    通常为 https://你的用户名.github.io/voxhub-portal/。最终以部署工作流与 Pages 设置显示的地址为准。全部资源使用相对路径，兼容仓库子路径和自定义域名。

也可使用传统的“Deploy from a branch”方式，选择包含源文件的分支与根目录；站点不需要 Jekyll 或服务端渲染。
