# 15 · 外部拨号引擎

`voxai-dialer` 是独立运行的外呼任务执行器。通过企业管理员凭据调用 `voxai-admin` 管理任务和名单，通过独立的企业令牌调用 `voxai-call` 发起客户优先外呼。执行器不直接连接数据库、Redis 或 FreeSWITCH。

## 1. 执行链路

```text
voxai-dialer 定时轮询
  → voxai-admin：任务 / 待确认命令 / 未完成 attempt
  → 先恢复未完成拨打：续租 → 查话单或媒体 → 回写结果
  → 处理 start / resume / pause / close 并 ack
  → 查询容量 → 领取名单
  → voxai-call：校验企业 / 任务 / 租约 / 时间窗 / 目标 / 容量
  → 事务保留 call_id / media_host / dispatch_time
  → 再次校验任务和租约后，FreeSWITCH originate 客户腿
  → 客户接通，进入原有技能组 ACD、指定坐席或 IVR
  → 原有话单管道落库
  → voxai-dialer 将结果转换为任务域的秒时间戳并回写
```

一份执行器配置绑定一个企业。多个副本可以轮询同一企业，名单领取和拨号保留均在数据库中加锁、去重；同一 attempt 的重复请求只返回已分配的 callId，不会重新 originate。调度器没有依赖本机内存的在途任务清单，重启后从数据库重建。

## 2. 调度策略

- `cruise`：保持固定并发；人工目标同时受空闲坐席承接量限制。IVR 目标无需坐席，但仍受任务和企业配额约束。
- `predictive`：只支持技能组或指定坐席。用过去一小时已完成拨打的客户接通率预测所需线路数，默认最多放大到空闲坐席数的两倍。样本不足 20 通或客户接通后未桥接的比例超过 3% 时，退回一名空闲坐席对应一路电话。
- 任务 `concurrency`、企业配置的正数 `outbound_limit`、执行器侧企业上限 `company-concurrency` 共同限制任务拨号。企业未配置正数 `outbound_limit` 时，使用 `company-concurrency`。同企业多个任务对同一人工目标的在途拨打共同占用承接量。
- 没有空闲坐席时，不对人工目标新增拨号。承接量只读取真实 `READY`、无 callId、已登录的坐席。
- `call_timeout` 传给 FreeSWITCH 的 `originate_timeout`。客户接通后还会设置媒体侧最长通话时长，默认 3600 秒。
- `close_time` 到期或名单全部结束时，执行器发出 `close` 命令。等待重拨间隔的名单仍计入待完成数量，不会被提前关闭。

这是受限的接通率预测策略，未引入平均通话时长预测、机器学习模型或基于未来坐席释放的调度。人工接通率和弃呼比例是动态采样，不保证每一通接通电话都能立即分配坐席。人工目标的排队、溢出继续使用技能组原有策略。

`company-concurrency` 约束本引擎发起的任务呼叫；手动外呼和其他系统直接创建的通道尚未统一纳入这个原子配额。企业总通道、运营商 CPS 和计费额度仍需在网关或统一呼叫入口另行限制。

## 3. 命令、租约和重拨

启动和恢复只有在媒体节点、数据源、目标及外显配置校验通过后才 ack。配置或网络故障时保持待确认状态，并在后续轮询重试；修复配置后无需重建任务。

暂停和关闭采用平滑停止：数据库中的待确认命令立即阻止新拨打，执行器确认命令后继续处理已有电话的续租与结果。它们不会主动挂断已接通客户。归档必须等全部 attempt 完成。

未分配 callId 的租约过期后允许重新领取，过期领取不消耗实际拨号轮次。分配了 callId 的 attempt 不会因租约超时自动回收。恢复执行器可以使用原租约令牌续租，先确认原呼叫结束，再回写并由服务端决定是否重拨。原 worker 不能用其他 callId 覆盖已分配呼叫。

`busy`、`no_answer`、`failed` 按 `retry_interval` 和 `call_rounds` 重拨；`answered`、`rejected`、`invalid` 不再重拨。客户接通但未分配坐席同样归为 `answered`，以免把已经接通的客户再次自动拨打；相应话单 `answer_flag=3` 用于预测降速。

## 4. 崩溃和连接故障

保留 callId 与真正 originate 是两个步骤。第一次派发在事务内重新锁定企业、任务和 attempt；过期、已停止或已被处理的保留不能迟到发起呼叫。

HTTP 超时、后台 originate 结果丢失均不会触发第二次 originate。执行器后续按原 attempt 查询状态。正常完成以数据库最终主话单和客户腿为准。任务呼叫的最终快照即使在压力模式下也同步提交主话单、月表、明细和通知任务后再清理 Redis，避免队列积压被误判为需要补偿；其他话单写入仍可使用异步管道。恢复补写遵循配置的 `cdr.notify.version`。

如果挂断事件丢失，超过呼叫超时加 30 秒后核对固定媒体节点上的通道；状态补偿与同 callId 已排队的媒体事件串行执行，避免覆盖正在处理的挂机快照。Redis 上下文仍存在时恢复本机设备索引，媒体事件也可根据 `variable_callId` 恢复索引。上下文丢失时，扫描通道的 callId 确认归属，终止失去上下文的残留通道，等待下一轮确认通道确实不存在后补写失败话单。FreeSWITCH 失联或返回不明确时保留 attempt，不推测呼叫已结束、不新增重复拨号。

人工通话结束后进入 `AFTER`，话后截止时间保存在 Redis，期满恢复 `READY` 并通知坐席。期间手动切为 `NOT_READY` 或退出的坐席不会被定时器强制改回 `READY`。

## 5. 数据库升级

依次执行：

1. 已有的 [任务安全迁移](sql/migration_20261107_task_safety.sql)，执行过的环境不要重复运行。
2. 新增的 [拨号日志迁移](sql/migration_20261107_task_dialer.sql)，增加 `cc_task_attempt.media_host`、`dispatch_time` 和 `call_id` 唯一索引。

新脚本需在启用引擎前完成，旧应用需与新应用一起升级租约回收逻辑，不能混用会自动回收已分配 callId 的旧版本。本次实现验证使用隔离测试库，未自动修改业务库。

## 6. 启用与运行

默认 `dialer.enabled=false`，`dialer.control.enabled=false`，不会自动发起呼叫。

先创建属于目标企业的专用管理员账号，用于受控服务间 Basic 认证。再生成至少 32 字符的随机服务令牌，在 `voxai-call` 和执行器两端使用相同值。每个企业配置不同的令牌。跨主机部署使用 HTTPS 或受保护的服务网络。

为 `voxai-call` 配置 [示例配置](examples/dialer-call.properties)，将其中企业 ID `1` 改为实际 ID；也可在现有 Nacos 配置中加入对应键。令牌通过环境变量 `DIALER_CALL_TOKEN` 提供。

```properties
dialer.control.enabled=true
dialer.control.tokens[1]=${DIALER_CALL_TOKEN}
dialer.control.company-concurrency=20
dialer.control.max-call-seconds=3600
dialer.control.max-predictive-ratio=2.0
dialer.control.max-abandon-rate=0.03
```

本引擎沿用调用节点内存中的 ACD 队列，`DIALER_CALL_URL` 必须固定到实际负责该企业的呼叫节点，避免请求在多个具有独立 ACD 队列的节点之间随机分发。客户腿和坐席腿固定到同一 FreeSWITCH 节点。多呼叫节点部署必须设置不同的 `SNOWFLAKE_WORKER_ID` / `SNOWFLAKE_DATACENTER_ID` 组合，避免生成重复通话 ID。

呼叫节点重启后，内存中尚未分配坐席的 ACD 排队不会自动重建；这类客户通道最终受媒体最长时长和状态补偿收尾。本实现提供拨打日志恢复和防重复拨号，ACD 排队的持久化及跨节点接管仍需单独实现。

构建：

```bash
mvn -pl voxai-dialer -am package -DskipTests
```

通过部署环境或密钥管理配置以下变量：

```text
DIALER_ENABLED=true
DIALER_COMPANY_ID=实际企业ID
DIALER_ADMIN_USER=该企业专用管理员
DIALER_ADMIN_PASSWORD=管理员密码
DIALER_CALL_TOKEN=该企业服务令牌
DIALER_ADMIN_URL=http://127.0.0.1:7100/voxai-admin
DIALER_CALL_URL=http://127.0.0.1:7200/voxai-call
```

运行：

```bash
java -jar voxai-dialer/target/voxai-dialer-1.0.0.jar
```

也可在准备好环境变量和 jar 后，执行 `docker compose -f voxai-dialer/docker-compose.yml up -d --build`。

任务仍从管理端创建、导入名单并发出 start。请配置真实启用的数据源、号码字段、转接 ID，以及外显号码或号码池。号码池只选取同企业、已启用的有效外显号码；显式号码与号码池同时配置时，该号码必须属于该池。

## 7. 新接口与单位

管理端接口复用原来的企业认证：

```text
GET /config/task/engine?afterId=0&limit=100
GET /config/task/{id}/attempt/active?afterAttemptId=&limit=100
GET /config/task/{id}/engine/pending
```

任务和 active attempt 均按游标分页；暂停、关闭后仍有在途拨打的任务也会被返回。

呼叫控制接口要求 `Authorization: Bearer <企业服务令牌>` 和 `X-Company-Id`，不接受请求 JSON 改写企业身份：

```text
GET  /internal/dialer/task/{id}/capacity
POST /internal/dialer/task/{id}/dial
POST /internal/dialer/task/{id}/status
```

后两个接口请求体为 `{"attemptId":"...","leaseToken":"..."}`，任务、名单、号码、目标及 callId 由服务端查库确定。capacity 返回允许新增的拨号数量，真正派发时在企业行锁下再次校验。

CDR 保持毫秒，执行器返回结果中的 `answerTime`、`bridgeTime` 明确为 epoch seconds；名单 `call_time` 使用 dispatch_time。Java HTTP 客户端按 Long 解析通话 ID，不经过浮点数转换。

## 8. 验证与边界

`mvn test` 覆盖默认关闭、启动配置校验、预测限流、命令确认、重启恢复、重复派发、租约验证、企业认证、FreeSWITCH 指令组装和媒体失联时的保留行为。

可选 MySQL 集成测试使用 `TASK_TEST_JDBC_URL`、`TASK_TEST_JDBC_USER`、`TASK_TEST_JDBC_PASSWORD`，连接已迁移的隔离库，验证实际 Mapper SQL、字段映射、已派发租约不可回收和未派发租约可重试；测试 DML 在 finally 中回滚。

本地自动测试不会向真实客户发起电话。正式启用前还需使用受控号码验证运营商路由、SIP 接通与挂机、技能组分配、IVR 可用性和真实话单。

`status_notify` 和 `traffic_notify` 仍是预留地址，本次没有新增这两种业务通知的发送协议。完整话单推送继续使用企业 `notify_url` 的既有可靠回调管道。
