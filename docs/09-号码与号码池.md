# 09 · 号码管理与号码池

## 两类对象

**号码管理**维护企业的单个号码，保存在 `cc_company_phone`。`type` 表示号码用途：

- `1`：呼入号码。
- `2`：主叫显号。
- `3`：被叫显号。

**号码池**保存在 `cc_company_display`，用于把同一用途的多个号码组织成可复用集合。号码池和单个号码通过 `cc_company_phone_group` 关联，是多对多关系：一个池包含多个号码，同一号码也可以加入多个池。号码池自身也有 `type`（1 呼入、2 主叫显号、3 被叫显号），配置号码池时应让号码和号码池用途一致。

号码池还保存 `strategy`（号码选择策略文本，建表默认值为“随机”）和 `location`（归属地，默认空字符串）。这两个字段随号码池新增、编辑和查询持久化；当前呼叫侧选号仍按既有逻辑随机取号，保存策略或归属地不会自动启用轮询或归属地筛选。

例如，企业维护单个号码 `4008000001`、`4008000002`，类型为被叫显号；再建立“外呼被叫号码池”，把两个号码加入池中。技能组可以引用这个号码池，而运行时可从号码列表里挑选号码。

## 呼入号码：入口识别与 VDN 路由

客户拨打呼入号码时，呼叫服务使用 `cc_vdn_phone.phone` 查找 VDN 及租户，之后由 VDN 配置决定转 IVR、技能组、坐席、放音或外线：

```text
客户拨打特服号
  → cc_vdn_phone.phone 匹配
  → 找到 vdn_id
  → VDN 日程与路由配置
  → IVR / 技能组 / 坐席 / 放音 / 外线
```

因此，`cc_company_phone` 中 type=1 的号码、号码池 type=1 与实际入口表 `cc_vdn_phone` 是相关但不同的配置对象。当前入口匹配代码直接读取 `cc_vdn_phone`；号码池不会自动创建 VDN 绑定，也不能仅凭把号码放进 type=1 池就认为来电已经接通路由。号码管理页维护号码资源，实际接入关系仍需在 VDN 特服号配置中建立。

## 主叫显号与被叫显号

技能组 `cc_group` 保存两个号码池 ID：

- `caller_display_id`：主叫显号池。
- `called_display_id`：被叫显号池。

坐席外呼时，系统先使用坐席的主技能组查找号码池。WebSocket 外呼路径中，被叫显号优先级是：客户端请求显号 → 坐席配置的 `display` → 从技能组被叫显号池随机选择。SIP 坐席外呼处理也会从技能组被叫号码池取号码。组池返回的是启用状态的号码。

主叫显号是外呼呼叫中对外呈现的业务号码，应理解为主叫一侧的显示身份。SIP/WebRTC 路径当前通常把坐席工号作为主叫显号；手机登录路径代码意图在坐席显号缺失时从技能组主叫号码池取号，但当前实现判断条件检查的是尚未赋值的局部 `callerDisplay`，导致该分支不会正常运行。因此，不能仅通过配置主叫号码池就断言手机坐席主叫显号已生效。

示例：小王通过 SIP 坐席拨打客户。系统从其主技能组的被叫显号池选择一条线路侧号码作为被叫腿显号；外呼主叫显号在当前 SIP 路径使用小王工号。客户侧最终看到的号码还受 FreeSWITCH 拨号变量和运营商线路策略影响，不能只根据号码池名称推断最终显示结果。

如果外呼请求未提供显号、坐席也没有配置显号，且技能组没有有效的被叫显号号码，运行时可能无法生成显号或无法继续外呼。技能组引用的是号码池 ID，不是单个号码；池内号码由关联表提供。

## 外呼任务号码池字段

`cc_task_config.number_pool_name` 是任务配置上的名称字段。预测式/巡航式拨号引擎属于外部组件，本仓库的任务管理配置和名单数据不等于拨号引擎已读取并使用此字段。不要将任务的 `number_pool_name` 与技能组的 `caller_display_id` / `called_display_id` 自动视为同一套选择逻辑。

## 维护规则与当前注意事项

- 单个号码在同一企业内按号码文本查重；号码长度由接口约束为 4–16 位。
- 删除号码采用逻辑停用；被号码池关联的号码会被拒绝删除，应先从号码池移除。
- 编辑号码池会按提交的 `phoneIds` 重建完整关联集合；未提交的旧号码会被移出。
- 删除号码池会停用号码池记录。技能组仍可能保存其池 ID；删除前应先解除技能组引用，避免外呼时取不到可用号码。
- 当前号码管理前端使用“外显号码/透传/随机”等字符串类型，而后端号码接口接收数值 `type` 1–3；字段契约需校准后，页面类型才能可靠对应后端语义。
- `strategy`、`location` 已纳入号码池接口对象、实体与数据库映射；策略值目前按字符串保存，没有后端枚举校验，呼叫侧也尚未据此改变选号方式。页面配置“轮询”等策略或归属地筛选时，应视为已保存的配置元数据，不代表运行时已按其执行。
- 新建数据库时使用仓库建表脚本即可包含这两个字段；已有数据库升级时也要在 `cc_company_display` 增加 `strategy`（`varchar(32)`，默认“随机”）和 `location`（`varchar(100)`，默认空字符串），否则号码池查询/写入会因缺列失败。

## 数据关系

```text
cc_company
  ├─ cc_company_phone (企业单个号码 + 用途类型)
  └─ cc_company_display (企业号码池 + 用途类型)
         └─ cc_company_phone_group (号码池与号码关联)

cc_group.caller_display_id ──> 主叫显号池
cc_group.called_display_id ──> 被叫显号池

cc_vdn_phone.phone ──> 来电入口号码与 VDN 的直接映射
```

相关表结构见 [数据模型](03-数据模型.md)，呼入完整路由见 [业务流程](02-业务流程.md)。
