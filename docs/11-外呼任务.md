# 11 · 外呼任务

外呼任务由“任务配置、名单数据、外部拨号引擎、通话结果”组成。当前仓库的 `voxai-admin` 负责配置、租户隔离、任务命令确认、名单领取租约和结果回写；预测式、巡航式调度由独立模块 `voxai-dialer` 执行，真实呼叫复用 `voxai-call`。部署与恢复协议见 [外部拨号引擎](15-外部拨号引擎.md)。

## 1. 业务边界

```text
cc_task_source 数据源
        ↓
cc_task_field 字段定义（标记电话号码字段）
        ↓
cc_task_contact 客户名单
        ↓
cc_task_config 外呼任务
        ↓
cc_task_attempt 租约与拨打事实
        ↓
voxai-dialer 通过管理端/呼叫控制 API 调度
        ↓
voxai-call 校验、保留 call_id 并调用 FreeSWITCH
        ↓
cc_call_log → cc_call_device / cc_call_detail
```

本仓库已实现：

- 任务、数据源、字段和名单关系的管理模型；
- 管理端任务、数据源、字段、名单、暂停记录和统计查询接口；
- 话单中的 `task_id` 关联；
- 话单和设备、流程明细的持久化。

`voxai-dialer` 负责：

- 预测式或巡航式拨号算法；
- 并发之外的接通率、呼损率和坐席承接能力控制；
- 实际 `originate` 调用；
- 任务命令的执行，以及执行后调用 ack 接口确认。

本服务的名单领取和呼叫控制接口会执行配置的并发上限、每日呼叫时间窗、企业配额、目标承接能力和关闭时间检查；此并发仅限制本引擎发起的任务呼叫，不代表 FreeSWITCH、手动外呼或企业整体通道限额。

## 2. 任务配置

`cc_task_config` 描述“何时呼叫、呼叫谁、以什么并发和轮次运行，以及接通后转到哪里”。

| 字段 | 业务含义 |
| --- | --- |
| `name` | 任务名称 |
| `call_start_time` / `call_end_time` | 每天可呼时间窗，例如 `08:00:00` 至 `21:00:00` |
| `close_time` | 任务关闭时间 |
| `transfer_type` / `transfer_name` | 接通后的目标类型和展示名称，如技能组、IVR、坐席等 |
| `display_number` | 任务使用的外显号码 |
| `number_pool_id` / `number_pool_name` | 任务使用的号码池稳定 ID / 展示名称 |
| `cruise_type` | `cruise`（巡航）或 `predictive`（受限接通率预测） |
| `concurrency` | 任务允许的并发上限 |
| `call_rounds` / `current_round` | 最大轮次和当前轮次 |
| `call_timeout` | 单次外呼超时时间 |
| `after_call_duration` | 接通后的话后处理时间 |
| `status` | 当前状态：表注释定义为 `1` 运行、`2` 暂停、`3` 关闭 |
| `total_count` / `list_total` | 总数量和名单总量 |
| `dialed_count` | 已拨数量 |
| `completed_count` | 已完成数量 |
| `answered_count` | 接通数量 |
| `status_notify` | 任务状态通知地址 |
| `traffic_notify` | 流量或话务通知地址 |
| `pause_start_time` / `pause_end_time` | 当前暂停区间 |

`concurrency` 是任务层调度上限，不等同于企业套餐的总并发、FreeSWITCH 通道数或技能组可用坐席数。`voxai-dialer` 同时检查企业额度、在线坐席、技能组空闲量、正在通话数、号码池和时间窗。

`display_number` 和 `number_pool_name` 也不是同一个概念：前者是具体外显号码，后者是展示名称，运行时使用 `number_pool_id`。任务号码池不会自动等同于技能组的 `caller_display_id` / `called_display_id`；派发时会校验显式外显号码属于任务号码池。

## 3. 预测式与巡航式

### 3.1 预测式外呼

预测式外呼根据坐席空闲数和近一小时已完成拨打的接通率提前拨号。例如有 10 个空闲坐席时，系统在样本充足且呼损受控时可以增加拨号线路，希望客户接通时有坐席承接。当前实现未使用平均通话时长或未来坐席释放预测。

优点是坐席利用率和拨号效率较高；风险是可能出现客户接通但没有空闲坐席的情况，因此必须控制呼损率、弃呼率和等待时间。

### 3.2 巡航式外呼

巡航式外呼按固定并发或固定节奏拨号。例如保持 5 路并发，一路结束后再补充下一条名单。它更容易控制节奏，适合自动接听、机器人、IVR 或固定转接场景。

`cruise_type` 固定为 `cruise` 或 `predictive`。`voxai-dialer` 配合呼叫服务提供固定并发巡航和受限接通率预测：冷启动和弃呼超限时按一名空闲坐席对应一路拨号，预测默认最多放大两倍。预测模式只支持人工目标，IVR 使用巡航模式。

## 4. 数据源与字段

### 4.1 `cc_task_source`

数据源表示一批客户数据的来源，例如 Excel、CRM 同步、第三方 API 或多轮次名单。主要字段为：

- `name`：数据源名称；
- `company_id`：所属企业；
- `status`：数据源状态；
- `field_count`：有效字段数量，列表查询时动态统计；
- `list_count`：通过该数据源关联任务动态统计的名单数量。

### 4.2 `cc_task_field`

字段定义通过 `source_id` 归属数据源：

- `name`：字段名；
- `is_phone`：是否电话号码字段，`1` 是，`0` 否；
- `field_type`：系统字段或自定义字段；
- `status`：字段状态。

一个数据源可以绑定多个字段。更新绑定时，管理接口会先清空原关联，再批量设置新的字段 ID。`voxai-dialer` 使用 `is_phone=1` 的字段作为可拨号码来源。

## 5. 客户名单

`cc_task_contact` 是 `voxai-dialer` 通过管理端租约接口消费的名单表。

| 字段 | 业务含义 |
| --- | --- |
| `task_id` | 所属任务 |
| `name` / `phone` | 客户名称和号码 |
| `current_round` | 当前呼叫轮次 |
| `uuid` | 名单记录稳定标识，供引擎幂等领取 |
| `call_time` / `answer_time` | 拨打和接通时间 |
| `call_status` | 呼叫阶段状态 |
| `call_result` | 最终呼叫结果 |
| `agent_code` | 承接坐席编号 |
| `bridge_time` | 桥接时间 |

`call_status` 表示名单处理阶段；本服务领取时写 `dialing`，回写后写 `retry` 或 `completed`。`call_result` 表示一次呼叫结果，建议对接双方固定字典：

```text
answered    已接通
no_answer   无人接听
busy        忙线
rejected    拒接
invalid     无效号码
failed      呼叫失败
completed   其他已完成结果
```

名单阶段状态还包括 `pending`（待拨）、`dialing`（持有租约/拨打中）、`retry`（等待重拨）和 `completed`（不再重拨）。引擎和管理端必须统一大小写和取值，否则统计筛选会产生分歧。

## 6. 轮次与暂停

`call_rounds` 表示客户最多允许的呼叫轮次，`current_round` 表示当前执行轮次。例如第一轮无人接听、第二轮忙线、第三轮接通，最终结果由 `voxai-dialer` 通过结果接口写入名单记录。

当前轮次规则：

- `busy`、`no_answer`、`failed` 允许进入下一轮，等待 `retry_interval` 秒；
- 每轮均受任务每日时间窗和关闭时间限制；
- `answered`、`rejected`、`invalid` 直接结束，客户接通但未分配坐席也不再自动重拨；
- 达到 `call_rounds` 后名单进入 `completed`，保存最后一次结果。

`cc_task_config.pause_start_time` / `pause_end_time` 表示当前暂停状态，`cc_task_pause` 保存暂停历史。前者用于快速读取当前状态，后者用于审计和统计。`voxai-dialer` 实现 command/ack 协议：启动/恢复先校验呼叫条件，暂停/关闭阻止新呼叫并让在途电话自然结束；暂停历史随确认状态更新。

## 7. 接通后的转接和号码

`transfer_type` / `transfer_name` 描述客户接通后的业务去向，可能是技能组、坐席、IVR、外线或机器人。`transfer_name` 是展示名称，不应作为稳定关联键；生产对接应另行约定目标 ID、编码或可解析的 `transfer_value`。

任务通过稳定的 `transfer_id` 指向技能组、坐席或 IVR。派发时校验企业归属和启用状态，客户接通后使用原有 ACD/坐席/IVR 链路承接。

## 8. 话单关联和结果回写

`voxai-dialer` 通过 `voxai-call` 发起通话时，会将任务 ID 写入呼叫上下文，使最终主话单保存：

```text
cc_call_log.task_id = cc_task_config.id
```

结束后按以下关系回查：

```sql
select * from cc_call_log where task_id = ?;
select * from cc_call_device where call_id = ?;
select * from cc_call_detail where call_id = ?;
```

`cc_call_log` 保存一次通话的整体结果，`cc_call_device` 保存坐席、客户、外线等设备腿，`cc_call_detail` 保存 VDN、IVR、技能组、按键和外线等流程轨迹。

`voxai-dialer` 轮询最终话单并通过结果接口更新 `cc_task_contact`。结果同时校验 task、contact、attempt、request 和租约令牌；callId 在真正 originate 前保留，同一拨打不可改为其他 callId。话单延迟时继续续租，暂停或关闭后仍继续结果回写。

## 9. 任务统计

管理端通过 `GET /taskStat` 查询任务监控。返回字段包括名单总量、已拨、接通、接通率、待拨、通话中、排队、登录坐席、空闲坐席、忙碌坐席、话后坐席和弃呼数。

当前 `TaskStatMapper` 主要从 `cc_task_config`、`cc_task_contact`、`cc_task_attempt` 和 `cc_agent_state_log` 动态计算结果，并不是读取一张独立的 `cc_task_stat` 快照表。排队、话后和弃呼没有对应的实时数据源，返回 `null` 表示不可用；已拨仅统计已回写 `call_id` 的呼叫，接通率以已回写呼叫为分母。

- `queue_count`；
- `after_call_agents`；
- `abandoned_count`。

因此这些字段目前代表接口预留值，不能直接当作完整实时指标。

## 10. 时间单位

任务域和新版话单的时间单位目前不完全一致：

| 范围 | 当前单位 |
| --- | --- |
| `cc_task_config.cts` / `uts` | 秒，管理端使用 `Instant.now().getEpochSecond()` |
| `close_time`、暂停时间 | 由任务域约定，历史数据通常为秒 |
| `cc_task_contact.call_time` / `answer_time` / `bridge_time` | 由 `voxai-dialer` 写入，统一使用任务域 epoch seconds |
| 新版 `cc_call_log` 时间点 | 毫秒 |
| 新版 `cc_call_device` 时间点 | 毫秒 |
| 新版话单时长 | 毫秒 |

跨任务表和话单表查询时，不能把所有 `Long` 都当成同一单位。对接协议应明确写出 `epoch seconds` 或 `epoch milliseconds`；若要统一任务域，必须单独迁移历史数据。

任务命令通过 command/ack 与 `voxai-dialer` 确认；名单领取、心跳续租和结果回写由管理端提供。预测式/巡航式拨号算法已由独立模块实现，默认关闭，需显式配置和启用。

## 12. 多租户和对接注意事项

任务、数据源和字段带有 `company_id`，业务数据应按企业隔离。`voxai-dialer` 通过绑定企业的认证读取任务和名单，不能只按自增 ID 查询。

任务管理路径在服务和 SQL 层按企业限定；其他旧版企业配置接口不都由本次改造覆盖，仍需单独审计。

`status_notify`、`traffic_notify` 目前只有字段，没有本仓库实现的接收端、签名、重试和响应协议；使用前需要另行确定。

## 13. 当前限制

1. 预测模式采用受限接通率预测，未实现平均通话时长或未来坐席释放预测。
2. 暂停和关闭采用平滑停止，已有呼叫继续自然结束。
3. 名单领取由管理端维护租约和 attempt；`voxai-dialer` 负责真实拨号并提交结果。
4. 排队、话后和弃呼指标仍是预留值。
5. 任务域和话单域存在秒、毫秒混用，报表必须按字段确认单位。
6. ACD 队列仍在呼叫节点内存中，执行器须固定到负责企业的调用节点；企业总通道/CPS 尚未形成覆盖手动外呼的统一原子配额。

## 14. 修复后的安全使用约定

- 管理端必须先通过登录接口获取 Redis 会话 token；无 token、过期 token、用户或企业停用时返回 `401`。Basic 认证仅用于受控运维场景，不能作为前端登录替代。
- 任务、数据源、字段、名单和暂停记录的读写都按 `company_id` 限定。详情、删除、字段绑定不能只传自增 ID。
- 创建任务默认是“已暂停”，需要通过 `POST /config/task/{id}/command` 提交 `start`、`pause`、`resume` 或 `close` 命令，再由 `voxai-dialer` 调用 `.../ack` 确认。页面修改只允许已暂停且没有待确认命令的任务。
- 任务配置使用稳定的 `sourceId`、`transferId` 和 `numberPoolId`；`transferName`、`numberPoolName` 只用于展示。旧任务需要补齐这些 ID 后才能启动。
- 名单导入使用批量接口，单批最多 500 条；每条记录必须有唯一 `uuid`、合法号码和 JSON 对象形式的 `customData`。名单查询按页返回。
- `voxai-dialer` 先调用 `/claim` 领取名单。返回的 `attemptId`、`leaseToken` 和 `leaseUntil` 必须原样保存；拨号期间用 `/heartbeat` 续租，结束时用 `/attempt/result` 回写。仅未分配 callId 的过期租约重新进入 `retry`。已分配 callId 的拨打须先核对通道与话单，不能因引擎失联直接重拨。
- `call_id`、`task_id`、`contact_id` 和 `attempt_id` 是完整关联链路。发起 FreeSWITCH 呼叫时应把 `task_id` 放入呼叫事件，系统会校验任务属于当前企业并写入主话单。
- `cc_task_attempt` 是每一次拨打的事实表，任务统计从名单和拨打记录动态计算。排队、话后和弃呼没有真实数据时返回 `null`，不能把预留的 `0` 当作真实零值。

结果回写会验证主话单的企业和任务归属，同一话单只能关联一次拨打。主话单异步落库尚未完成时，引擎应继续续租并重试回写。归档前必须等待所有拨打完成或租约过期；通知 URL 最长 64 字符，与现有数据库列一致。

对应迁移脚本：[任务安全](sql/migration_20261107_task_safety.sql)、[引擎拨号日志](sql/migration_20261107_task_dialer.sql)。必须先完成数据库迁移，再发布依赖新列和 `cc_task_attempt` 的应用版本；旧数据需要由运营补齐稳定关联 ID。
