# 11 · 外呼任务

外呼任务由“任务配置、名单数据、外部拨号引擎、通话结果”组成。当前仓库的 `voxai-admin` 负责任务和名单的配置管理；预测式、巡航式拨号调度器不在本仓库内，外部引擎通过数据库读取任务，负责实际拨号、并发控制和名单结果回写。

## 1. 业务边界

```text
cc_task_source 数据源
        ↓
cc_task_field 字段定义（标记电话号码字段）
        ↓
cc_task_contact 客户名单
        ↓
cc_task_config 外呼任务
        ↓
外部拨号引擎读取并调度
        ↓
FreeSWITCH originate / 桥接
        ↓
cc_call_log → cc_call_device / cc_call_detail
```

本仓库已实现：

- 任务、数据源、字段和名单关系的管理模型；
- 管理端任务、数据源、字段、名单、暂停记录和统计查询接口；
- 话单中的 `task_id` 关联；
- 话单和设备、流程明细的持久化。

外部引擎负责：

- 预测式或巡航式拨号算法；
- 从名单中选取下一通电话；
- 并发、接通率、呼损率和坐席承接能力控制；
- 实际 `originate` 调用；
- `cc_task_contact` 的呼叫状态和结果回写；
- 任务启动、暂停、恢复和结束调度。

## 2. 任务配置

`cc_task_config` 描述“何时呼叫、呼叫谁、以什么并发和轮次运行，以及接通后转到哪里”。

| 字段 | 业务含义 |
| --- | --- |
| `name` | 任务名称 |
| `call_start_time` / `call_end_time` | 每天可呼时间窗，例如 `08:00:00` 至 `21:00:00` |
| `close_time` | 任务关闭时间 |
| `transfer_type` / `transfer_name` | 接通后的目标类型和展示名称，如技能组、IVR、坐席等 |
| `display_number` | 任务使用的外显号码 |
| `number_pool_name` | 任务使用的号码池名称 |
| `cruise_type` | 外呼方式标识，常见语义为预测式或巡航式；具体枚举由外部引擎约定 |
| `concurrency` | 任务允许的并发上限 |
| `call_rounds` / `current_round` | 最大轮次和当前轮次 |
| `call_timeout` | 单次外呼超时时间 |
| `after_call_duration` | 接通后的话后处理时间 |
| `status` | 当前状态：表注释定义为 `1` 运行、`2` 暂停、`3` 关闭 |
| `total_count` / `list_total` | 总数量和名单总量 |
| `dialed_count` | 已拨数量 |
| `completed_count` | 已完成数量 |
| `answered_count` | 接通数量 |
| `status_notify` | 任务状态通知地址 |
| `traffic_notify` | 流量或话务通知地址 |
| `pause_start_time` / `pause_end_time` | 当前暂停区间 |

`concurrency` 是任务层调度上限，不等同于企业套餐的总并发、FreeSWITCH 通道数或技能组可用坐席数。外部引擎应同时检查企业额度、在线坐席、技能组空闲量、正在通话数、号码池和时间窗。

`display_number` 和 `number_pool_name` 也不是同一个概念：前者是具体外显号码，后者是号码池名称。任务号码池不会自动等同于技能组的 `caller_display_id` / `called_display_id`，两套配置需要外部引擎明确关联。

## 3. 预测式与巡航式

### 3.1 预测式外呼

预测式外呼根据坐席空闲数、历史接通率、平均通话时间等指标提前拨号。例如有 10 个空闲坐席时，系统可能同时拨打多于 10 个号码，希望部分号码接通时正好有坐席承接。

优点是坐席利用率和拨号效率较高；风险是可能出现客户接通但没有空闲坐席的情况，因此必须控制呼损率、弃呼率和等待时间。

### 3.2 巡航式外呼

巡航式外呼按固定并发或固定节奏拨号。例如保持 5 路并发，一路结束后再补充下一条名单。它更容易控制节奏，适合自动接听、机器人、IVR 或固定转接场景。

当前代码只保存 `cruise_type` 字符串，没有实现上述两种调度算法。不能仅凭该字段判断本仓库已经提供了预测式拨号能力。

## 4. 数据源与字段

### 4.1 `cc_task_source`

数据源表示一批客户数据的来源，例如 Excel、CRM 同步、第三方 API 或多轮次名单。主要字段为：

- `name`：数据源名称；
- `company_id`：所属企业；
- `status`：数据源状态；
- `field_count`：有效字段数量，列表查询时动态统计；
- `list_count`：名单数量字段，当前查询实现没有完整统计逻辑。

### 4.2 `cc_task_field`

字段定义通过 `source_id` 归属数据源：

- `name`：字段名；
- `is_phone`：是否电话号码字段，`1` 是，`0` 否；
- `field_type`：系统字段或自定义字段；
- `status`：字段状态。

一个数据源可以绑定多个字段。更新绑定时，管理接口会先清空原关联，再批量设置新的字段 ID。外部引擎应使用 `is_phone=1` 的字段作为可拨号码来源。

## 5. 客户名单

`cc_task_contact` 是外部引擎实际消费的名单表。

| 字段 | 业务含义 |
| --- | --- |
| `task_id` | 所属任务 |
| `name` / `phone` | 客户名称和号码 |
| `current_round` | 当前呼叫轮次 |
| `uuid` | 外部引擎或名单记录标识 |
| `call_time` / `answer_time` | 拨打和接通时间 |
| `call_status` | 呼叫阶段状态 |
| `call_result` | 最终呼叫结果 |
| `agent_code` | 承接坐席编号 |
| `bridge_time` | 桥接时间 |

建议对接双方固定状态字典，例如：

```text
pending    待拨
dialing    拨打中
ringing    振铃中
answered   已接通
no_answer  未接通
busy       忙线
rejected   拒接
invalid    无效号码
failed     呼叫失败
completed  已完成
```

当前实体没有状态枚举，样例数据使用过 `answered`、`no_answer`、`success`、`failed` 等字符串。引擎、报表和管理端必须统一大小写和取值，否则统计筛选会产生分歧。

## 6. 轮次与暂停

`call_rounds` 表示客户最多允许的呼叫轮次，`current_round` 表示当前执行轮次。例如第一轮无人接听、第二轮忙线、第三轮接通，最终结果应由外部引擎写入名单记录。

需要由引擎约定的规则包括：

- 哪些结果允许进入下一轮；
- 每轮之间的等待时间；
- 是否限制重拨时间窗；
- 接通后是否立即终止后续轮次；
- 达到最大轮次后的最终状态。

`cc_task_config.pause_start_time` / `pause_end_time` 表示当前暂停状态，`cc_task_pause` 保存暂停历史。前者用于快速读取当前状态，后者用于审计和统计。当前仓库提供暂停记录查询，但没有完整实现拨号引擎的启动、暂停、恢复调度协议。

## 7. 接通后的转接和号码

`transfer_type` / `transfer_name` 描述客户接通后的业务去向，可能是技能组、坐席、IVR、外线或机器人。`transfer_name` 是展示名称，不应作为稳定关联键；生产对接应另行约定目标 ID、编码或可解析的 `transfer_value`。

当前任务表没有明确的 `transfer_id` 字段，外部引擎需要和管理端约定如何从 `transfer_type`、`transfer_name` 找到真实目标。

## 8. 话单关联和结果回写

外部引擎发起通话时，应将任务 ID 传入呼叫上下文，使最终主话单保存：

```text
cc_call_log.task_id = cc_task_config.id
```

结束后按以下关系回查：

```sql
select * from cc_call_log where task_id = ?;
select * from cc_call_device where call_id = ?;
select * from cc_call_detail where call_id = ?;
```

`cc_call_log` 保存一次通话的整体结果，`cc_call_device` 保存坐席、客户、外线等设备腿，`cc_call_detail` 保存 VDN、IVR、技能组、按键和外线等流程轨迹。

当前仓库不会在话单结束时自动更新 `cc_task_contact`。`call_status`、`call_result`、`agent_code` 和 `bridge_time` 仍由外部引擎负责回写。外部引擎应使用 `call_id` 或自身的 `uuid` 做幂等关联，避免重复回写名单。

## 9. 任务统计

管理端通过 `GET /taskStat` 查询任务监控。返回字段包括名单总量、已拨、接通、接通率、待拨、通话中、排队、登录坐席、空闲坐席、忙碌坐席、话后坐席和弃呼数。

当前 `TaskStatMapper` 主要从 `cc_task_config` 和 `cc_agent_state_log` 动态计算结果，并不是读取一张独立的 `cc_task_stat` 快照表。当前 SQL 中以下指标仍是固定的 `0`：

- `pending_count`；
- `queue_count`；
- `after_call_agents`；
- `abandoned_count`。

因此这些字段目前代表接口预留值，不能直接当作完整实时指标。

## 10. 时间单位

任务域和新版话单的时间单位目前不完全一致：

| 范围 | 当前单位 |
| --- | --- |
| `cc_task_config.cts` / `uts` | 秒，管理端使用 `Instant.now().getEpochSecond()` |
| `close_time`、暂停时间 | 由任务域约定，历史数据通常为秒 |
| `cc_task_contact.call_time` / `answer_time` / `bridge_time` | 由外部引擎写入，样例数据为秒 |
| 新版 `cc_call_log` 时间点 | 毫秒 |
| 新版 `cc_call_device` 时间点 | 毫秒 |
| 新版话单时长 | 毫秒 |

跨任务表和话单表查询时，不能把所有 `Long` 都当成同一单位。对接协议应明确写出 `epoch seconds` 或 `epoch milliseconds`；若要统一任务域，必须单独迁移历史数据。

## 11. 管理端接口

任务接口位于 `CompanyController`：

```text
GET    /task
GET    /task/{id}
POST   /task
PUT    /task/{id}
DELETE /task/{id}
GET    /task/{taskId}/contact
GET    /task/{taskId}/pause

GET    /taskSource
GET    /taskSource/{id}
POST   /taskSource
PUT    /taskSource/{id}
DELETE /taskSource/{id}

GET    /taskField
POST   /taskField
PUT    /taskField/{id}
DELETE /taskField/{id}
GET    /taskSource/{sourceId}/fields
PUT    /taskSource/{sourceId}/fields

GET    /taskStat
```

这些接口提供配置和查询能力，不代表拨号引擎已经集成。对接时还需要定义任务启动、暂停、恢复、名单导入、结果回写和状态通知协议。

## 12. 多租户和对接注意事项

任务、数据源和字段带有 `company_id`，业务数据应按企业隔离。外部引擎读取任务和名单时必须带企业条件，不能只按自增 ID 查询。

部分详情、删除和名单查询接口当前没有在方法内部显式校验企业归属。部署前应通过权限拦截器、网关或补充控制器校验，避免跨企业读取或修改任务数据。

`status_notify`、`traffic_notify` 目前只有字段，没有本仓库实现的接收端、签名、重试和响应协议；使用前需要与外部引擎另行确定。

## 13. 当前限制

1. 预测式和巡航式拨号算法不在本仓库。
2. 任务启动、暂停、恢复和停止协议没有完整对外定义。
3. 名单导入和 `cc_task_contact` 结果回写由外部引擎负责。
4. 任务统计中的部分指标是预留的固定值。
5. 任务域和话单域存在秒、毫秒混用，报表必须按字段确认单位。
6. 任务转接目标缺少稳定的目标 ID 字段，需要对接方补充约定。
