# 话单一致性与回调

系统把一次通话拆成三层数据：`cc_call_log` 是一次通话的主记录，`cc_call_device` 是每个 FreeSWITCH 分机腿，`cc_call_detail` 是进入技能组、转接、IVR 等流程节点的轨迹。三张表都以 `call_id` 关联；设备使用 `(call_id, device_id)` 幂等，流程使用 `(call_id, detail_index)` 幂等。

通话结束时，系统在同一个事务中写入当前表、按通话创建月份写入月表，并创建回调 outbox 记录。压力模式的 Rabbit 消费者和同步路径使用同一个事务写入器；消息异常会抛回容器，由 Rabbit 重投，不能确认一条只写入部分表的消息。月表使用 `CREATE TABLE IF NOT EXISTS ... LIKE ...` 按需创建，并在启动时准备当月和下月。月表 DDL 在事务外执行，避免 MySQL 隐式提交话单事务。

时间点字段统一为 Unix epoch **毫秒**：`cts`、`uts`、`call_time`、`answer_time`、`end_time`、`record_start_time` 以及流程的 `start_time`/`end_time`。时长字段也统一为毫秒：`talk_time`、`record_time`、`wait_time`。FreeSWITCH 的 `Event-Date-Timestamp` 是微秒，代码除以 `1000` 得到毫秒。读取旧数据时，兼容层会把明显的秒级时间点转换成毫秒，但不会转换时长；旧数据的筛选条件仍应按对应历史表和迁移策略确认。

录音开始事件只设置 `record_start_time`，并把录音时长重置为 `0`。挂机时按 `end_time - record_start_time` 计算 `record_time`，负值或缺失值按 `0` 处理。主话单的录音地址和起点取最早有录音的设备腿。

## 回调

企业配置 `cc_company.notify_url` 后，结束事务会把通知写入 `cc_cdr_notify`，由后台 dispatcher 在提交后 POST。发送采用可恢复租约、指数退避和最大重试次数，成功状态为 `2`，超过次数为 `3`；同一 `call_id` 可能重复投递，接收端应以 `call_id` 去重，并在收到通知后回查数据库确认明细。

默认 `cdr.notify.version=1`，保持原有 `CallLogPo` 结构，包含主话单和 `callDeviceList`，不包含 `callDetailList`。设置 `cdr.notify.version=2` 后，载荷增加 `cdrVersion=2`、`timestampUnit=epochMillis`、`durationUnit=milliseconds` 和 `callDetailList`；根对象及嵌套对象的 `callId` 以字符串传输，避免 JavaScript 精度丢失。V1/V2 的回调都在 durable CDR 事务提交后才发送。

## 部署与排查

上线前先执行 [migration_20261106_cdr_consistency.sql](sql/migration_20261106_cdr_consistency.sql)。迁移为三类 CDR 表补充自然键并创建 `cc_cdr_notify`；发现重复自然键时会失败并停止，不会自动删除数据。历史秒级时间点和历史时长没有自动批量改写，需由数据团队按业务窗口单独核对。

常用排查 SQL：

```sql
select call_id, status, push_times, next_attempt_at, push_response
from cc_cdr_notify where status in (1, 3) order by next_attempt_at;

select l.call_id, l.month_time,
       (select count(*) from cc_call_device d where d.call_id = l.call_id) device_count,
       (select count(*) from cc_call_detail f where f.call_id = l.call_id) detail_count
from cc_call_log l where l.call_id = ?;
```

当前 CDR upsert、月表建表和 outbox SQL 使用 MySQL 语法；其他数据库方言不能直接套用该迁移和异步写入路径。
